## 1. 认证机制概述

系统使用自定义 Token 拦截器（**非 Apache Shiro**），核心逻辑：

```
请求进入
  │
  ├── 路径是 /dictionary/page 或 /file/upload 或 /yonghu/register？
  │     → 直接放行
  │
  ├── 方法上有 @IgnoreAuth 注解？
  │     → 直接放行（无需登录）
  │
  ├── Header 中携带有效 Token？
  │     → 解析 Token，将 userId / role / tableName / username 写入 Session
  │     → 放行
  │
  └── 以上都不满足
        → 返回 401 "请先登录"
```

**角色信息存储在 Token 中**，登录后由 `TokenService` 生成并返回。Session 中的 `role` 属性即为角色名（中文字符串）。

## 6. 文档-前端不一致问题

### 6.1 recharge.html 无后端接口

**问题描述**：

前端存在充值页面 `front/pages/recharge/recharge.html`，提供了微信支付、支付宝支付、建设银行、农业银行、中国银行、交通银行六种支付方式的 UI，但**系统中不存在任何专用的充值/支付后端接口**。

**实际行为分析**：

```javascript
// recharge.html 中的提交逻辑
vue.user.newMoney = Number(vue.user.newMoney) + Number(data.newMoney);
http.requestJson(`${table}/update`, 'post', vue.user, function(data) {
    layer.msg('充值成功');
});
```

该页面的工作方式：
1. 从 `localStorage` 读取当前用户的 `table` 名（如 `jiaoshi` 或 `xuesheng`）
2. 调用 `GET /{table}/session` 获取当前用户信息
3. 在前端直接将充值金额加到 `user.newMoney` 字段上
4. 调用 `POST /{table}/update` 将整个用户对象回写

**安全风险**：

| 风险点 | 说明 |
|--------|------|
| 无支付网关对接 | 六种支付方式仅为 UI 展示，点击后不会跳转到真实支付页面 |
| 金额前端计算 | 余额在浏览器端累加，可被篡改（用户可修改 `newMoney` 为任意值） |
| 无服务端校验 | `/update` 接口不校验金额变化的合理性，直接接受前端传入的值 |
| 支付选择无效 | 选择不同银行/支付方式不影响实际行为，所有选项执行相同逻辑 |

**结论**：`recharge.html` 是一个**纯前端模拟页面**，没有对应的支付后端接口。如果系统不需要充值功能，建议在前端菜单中隐藏入口；如果需要，必须实现服务端支付逻辑。

### 6.2 其他已知不一致

| 项目 | 说明 |
|------|------|
| `batchInsert` 字段映射 | 所有控制器的 Excel 批量导入接口中，实体字段赋值代码均被注释掉，实际执行时会插入空实体 |
| `delete` / `delete1` 无权限 | 名片的软删除和硬删除接口没有角色校验，任何已登录用户均可调用。实际权限控制依赖前端按钮的显隐 |
| `/mingpian/detail/{id}` 需登录 | 前台名片详情页需要 Token 才能访问（无 `@IgnoreAuth`），但列表页不需要。可能导致未登录用户能看到列表却无法打开详情 |
| `/keyanchengguo/detail/{id}` 同上 | 科研成果详情页同样需要登录，与列表页的免登录策略不一致 |
