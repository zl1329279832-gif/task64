# 教师名片与科研成果数据规范

> 本文档从 MingpianController、KeyanchengguoController、MingpianCollectionController
> 源码反推，面向学院运维与集成方，描述名片及科研成果的字段语义、状态流转与版本约束。
>
> 适用版本：migration_v1.sql 之后的 schema（含 mingpian_history 表与 version_number 列）。

---

## 1 核心字段速查

### 1.1 名片表 `mingpian`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INT PK | 名片主键 |
| `jiaoshi_id` | INT FK | 所属教师，**唯一约束见 §3** |
| `version_number` | INT NOT NULL DEFAULT 1 | 当前名片的版本号，每提交一次新版本自增 1 |
| `shangxia_types` | INT | 上下架/审核状态，字典编码 `shangxia_types`，见 §4 |
| `mingpian_delete` | INT | 软删标记：**1 = 正常，2 = 已软删** |
| `mingpian_clicknum` | INT | 名片被浏览的次数，初始值 1，见 §6 |
| 其余业务字段 | — | mingpian_name / uuid_number / xingming / phone / file / photo / content 等 |

### 1.2 科研成果表 `keyanchengguo`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INT PK | 成果主键 |
| `jiaoshi_id` | INT FK | 所属教师 |
| `shangxia_types` | INT | 上下架状态（仅使用 1 = 上架；无审核流程） |
| `keyanchengguo_delete` | INT | 软删标记：**1 = 正常，2 = 已软删** |
| `keyanchengguo_clicknum` | INT | 成果被浏览的次数，初始值 1，见 §6 |

### 1.3 名片版本快照表 `mingpian_history`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INT PK | 快照主键 |
| `mingpian_id` | INT FK | 原名片 id（索引） |
| `jiaoshi_id` | INT FK | 所属教师（索引） |
| `version_number` | INT | 快照时的版本号（联合索引 mingpian_id + version_number） |
| `snapshot_time` | DATETIME | 快照生成时间 |
| `snapshot_reason` | VARCHAR | 快照原因（如"被V3替换"、"回退到V1时被归档"、"审核驳回"） |
| 其余字段 | — | 与 mingpian 表一一对应的全量快照，包括 mingpian_clicknum 和 shangxia_types |

## 2 软删与硬删

### 2.1 名片软删 `mingpianDelete`

| 操作 | 接口 | 实现 | 数据可恢复 |
|---|---|---|---|
| **软删** | `POST /mingpian/delete` | `UPDATE mingpian SET mingpian_delete = 2 WHERE id IN (...)` | 可恢复 |
| **硬删** | `POST /mingpian/delete1` | `deleteBatchIds()` — 物理删除行 | 不可恢复 |

- 软删后的名片在前台列表（`/mingpian/list`）和管理后台默认查询中**均被过滤**（`mingpian_delete = 1`）。
- 管理后台"名片回收站"模块可查询 `mingpian_delete = 2` 的记录，并调用 `delete1` 永久删除。
- **唯一约束检查包含软删条件**：新建名片时校验 `jiaoshi_id + mingpian_delete = 1` 是否已存在。
  也就是说，**已软删的名片不阻止该教师新建名片**。

### 2.2 科研成果软删 `keyanchengguoDelete`

| 操作 | 接口 | 实现 |
|---|---|---|
| **软删** | `POST /keyanchengguo/delete` | `UPDATE keyanchengguo SET keyanchengguo_delete = 2 WHERE id IN (...)` |

- 科研成果**没有硬删接口**，也无回收站模块。
- 查询默认过滤 `keyanchengguo_delete = 1`。

### 2.3 收藏表无软删

名片收藏（`mingpian_collection`）和科研成果收藏（`keyanchengguo_collection`）的删除均为**硬删**（`deleteBatchIds`），无软删字段。

## 3 名片唯一约束——不能同时两张有效

> **结论：同一教师在同一时刻只能有一张"有效"名片。**

"有效"的判定条件：`mingpian_delete = 1`（未软删）。

### 3.1 约束执行点

| 场景 | 代码位置 | 检查逻辑 |
|---|---|---|
| 后台新建名片 | `MingpianController.save()` | 查询 `jiaoshi_id = ? AND mingpian_delete = 1`，若已存在则拒绝 |
| 后台修改名片 | `MingpianController.update()` | 同上 |
| 教师提交新版本 | `MingpianController.submitVersion()` | 查询 `jiaoshi_id = ? AND shangxia_types = 2 AND mingpian_delete = 1`，若有待审核版本则拒绝 |

### 3.2 哪些状态可以"共存"

| 状态组合 | 是否允许 |
|---|---|
| 1 张已上架(1) + 1 张已软删(2) | 允许，软删不算有效 |
| 1 张已上架(1) + 1 张已归档(4) | 注意：归档版本的 `mingpian_delete` 仍为 1。`approveVersion` 归档时不修改 `mingpian_delete`，此时旧卡 shangxia=4、新卡 shangxia=1，两行 `delete=1` 共存。**唯一约束仅在 save/update 时检查**，approveVersion 流程内部不执行此检查。 |
| 1 张待审核(2) + 1 张已上架(1) | 允许。待审核版本是新行，`delete=1`，与当前上架版本共存——但 `submitVersion` 会检查"是否已有待审核版本"来防止重复提交 |
| 2 张已上架(1) | 拒绝。save/update 时拦截 |

> **运维注意**：`approveVersion` 和 `huitui` 内部不经过 `save` 的唯一约束检查，
> 因此数据库中可能出现同一教师多条 `mingpian_delete=1` 的记录（一条活跃 + 若干归档）。
> 这是设计预期，不是 bug，但运维排查时需注意。

## 4 上下架状态 `shangxiaTypes` 字典

字典编码 `shangxia_types`，由 `migration_v1.sql` 补充：

| 字典值 | 名称 | 适用表 | 说明 |
|---|---|---|---|
| **1** | 已上架 / 展示中 | mingpian, keyanchengguo | 前台可见；新建默认值 |
| **2** | 待审核 | mingpian | 教师提交新版本后的中间态，前台不可见 |
| **3** | 审核驳回 | mingpian | 管理员拒绝后标记，随后该名片被软删 |
| **4** | 已归档 | mingpian | 被新版本替换或被回退替换的旧版本，保留在数据库中 |

> 科研成果 `keyanchengguo.shangxia_types` 仅使用值 **1**（上架），
> 不经过审核流程。管理员在后台可直接修改该字段进行手动上下架。

## 5 版本生命周期与回退（huitui）

### 5.1 提交新版本 `submitVersion`

```
教师操作 → 系统创建一条新 mingpian 记录
         → shangxia_types = 2（待审核）
         → version_number = 当前最大版本号 + 1
         → mingpian_delete = 1
```

**前置约束**：该教师不能已有 `shangxia_types = 2` 的有效名片（防重复提交）。

### 5.2 审核通过 `approveVersion`

```
管理员操作 →
  1. 将当前活跃名片（shangxia=1）全量快照写入 mingpian_history
     - snapshot_reason = "被V{new_version}替换"
  2. 将当前活跃名片的 shangxia_types 改为 4（已归档）
  3. 将新版本名片的 shangxia_types 改为 1（上架）
```

### 5.3 审核驳回 `rejectVersion`

```
管理员操作 →
  1. 将待审核名片全量快照写入 mingpian_history
     - shangxia_types 快照值为 3（审核驳回）
     - snapshot_reason = 管理员填写的驳回理由
  2. 将待审核名片软删（mingpian_delete = 2）
```

### 5.4 回退 `huitui`

> 接口：`POST /mingpian/huitui?historyId={id}`

```
管理员或教师操作 →
  1. 权限校验：管理员可回退任意名片；教师只能回退自己的名片
  2. 从 mingpian_history 加载目标快照
  3. 查找该教师当前活跃名片（shangxia_types=1, mingpian_delete=1）
     a. 若活跃名片就是目标版本 → 报错"该版本已经是当前活跃版本"
     b. 若存在其他活跃名片 →
        - 将活跃名片快照写入 mingpian_history
          snapshot_reason = "回退到V{n}时被归档"
        - 将活跃名片 shangxia_types 改为 4（已归档）
  4. 用快照数据覆盖 mingpian 表中原名片记录（按 mingpian_id 定位）
     - shangxia_types = 1（上架）
     - mingpian_delete = 1
```

### 5.5 软删 vs 回退——对比

| 维度 | 软删 (delete) | 回退 (huitui) |
|---|---|---|
| **本质** | 标记名片为"已删除" | 用历史快照**覆盖**当前名片数据 |
| **数据变化** | 仅修改 `mingpian_delete` 字段 | 重写名片全部业务字段 + 状态字段 |
| **是否生成快照** | 否 | 是（归档当前活跃版本） |
| **可逆性** | 可恢复（改回 `mingpian_delete=1`） | 可通过再次回退到之前的版本还原 |
| **前台可见性** | 软删后前台不可见 | 回退后名片以上架状态重新可见 |
| **操作者** | 管理员 | 管理员或教师（教师限本人） |

## 7 科研成果与名片联合展示

### 7.1 展示逻辑

教师名片前台详情页（`/mingpian/detail/{id}`）会**同时返回该教师的科研成果列表**：

```
MingpianView.keyanchengguoList = List<KeyanchengguoView>
```

过滤条件：
- `keyanchengguo.jiaoshi_id = 当前名片的 jiaoshi_id`
- `keyanchengguo.shangxia_types = 1`（已上架）
- `keyanchengguo.keyanchengguo_delete = 1`（未软删）

### 7.2 对运维的含义

- 教师在前台看到的名片详情页，**自动聚合**了该教师所有上架且未删除的科研成果。
- 如需让某成果不在名片页显示：下架（`shangxia_types != 1`）或软删（`keyanchengguo_delete = 2`）即可。
- 名片本身被软删或下架后，前台无法访问该名片的详情页，自然也不会展示关联成果。

## 8 点击计数 `clicknum` 机制

### 8.1 名片点击 `mingpianClicknum`

- **触发时机**：前台用户访问名片详情页 `GET /mingpian/detail/{id}`。
- **实现方式**：**原子递增** — 通过 MyBatis XML 执行：
  ```sql
  UPDATE mingpian SET mingpian_clicknum = mingpian_clicknum + 1 WHERE id = #{id}
  ```
- **初始值**：名片创建时设为 1。
- **并发安全**：原子操作，无竞态条件。

### 8.2 科研成果点击 `keyanchengguoClicknum`

- **触发时机**：前台用户访问成果详情页 `GET /keyanchengguo/detail/{id}`。
- **实现方式**：**读-改-写**（非原子）：
  ```java
  entity.setKeyanchengguoClicknum(entity.getKeyanchengguoClicknum() + 1);
  service.updateById(entity);
  ```
- **初始值**：成果创建时设为 1。
- **并发安全**：高并发下可能丢失计数（两个请求同时读到相同值后各 +1，实际只增了 1）。
- **运维建议**：如需精确计数，可参照名片的 `incrementClickNum` 方式补充 DAO 层原子递增。

## 10 运维常见问题

### Q1：教师说"我的名片不见了"

1. 检查 `mingpian_delete` 是否为 2（被软删） → 改回 1 恢复。
2. 检查 `shangxia_types` 是否为 2/3/4 → 改为 1 重新上架。
3. 检查是否被 `approveVersion` 归档（shangxia=4） → 使用 `huitui` 回退。

### Q2：教师想同时展示两个方向的名片

**不支持。** 同一教师同一时刻只能有一张 `shangxia_types=1` 的名片。
可通过"提交新版本 → 审核通过"的方式切换名片内容，旧版本自动归档并可通过回退恢复。

### Q3：科研成果在名片详情页不显示

1. 检查成果的 `keyanchengguo_delete` 是否为 1。
2. 检查成果的 `shangxia_types` 是否为 1。
3. 检查成果的 `jiaoshi_id` 是否与名片的教师一致。

### Q4：回退后数据"丢失"

回退不会删除数据。被替换的当前版本会被快照到 `mingpian_history` 表并归档（shangxia=4）。
如需再次恢复，可对刚归档的版本再次执行 `huitui`。

### Q5：审核驳回后名片能否恢复

审核驳回后名片被**软删**（`mingpian_delete=2`），同时快照进入 `mingpian_history`。
- 从回收站恢复：修改 `mingpian_delete` 为 1，再根据需要设置 `shangxia_types`。
- 从历史回退：使用 `huitui` 接口，但注意回写的是快照时的数据。
