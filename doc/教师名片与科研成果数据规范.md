## 2. 软删除机制

### 2.1 名片软删除（mingpian_delete）

| 值 | 含义 | 说明 |
|:--:|------|------|
| `1` | 正常（未删除） | 默认值，创建时自动设置 |
| `2` | 已软删除 | 通过 `POST /mingpian/delete` 设置 |

**实现方式**（`MingpianController.delete`）：

```
遍历传入的 ids 数组
  → 对每条记录设置 mingpian_delete = 2
  → 调用 updateBatchById() 批量更新
```

- **不删除数据库行**，仅标记 `mingpian_delete=2`
- 后端列表查询（`/page`）自动过滤 `mingpian_delete=1`，因此软删除的记录不会出现在正常列表中
- 系统另有硬删除接口 `POST /mingpian/delete1`，调用 `deleteBatchIds()` 物理删除行——**不可逆**

### 2.2 科研成果软删除（keyanchengguo_delete）

| 值 | 含义 |
|:--:|------|
| `1` | 正常（未删除） |
| `2` | 已软删除 |

**实现方式**（`KeyanchengguoController.delete`）与名片完全一致：遍历 ids → 设置 `keyanchengguo_delete=2` → `updateBatchById()`。

**注意**：科研成果**没有**硬删除接口（无 `delete1` 端点）。

### 2.3 收藏表的删除

名片收藏（`mingpian_collection`）和科研成果收藏（`keyanchengguo_collection`）均为**硬删除**——调用 `deleteBatchIds()` 直接移除数据库行。收藏表不使用软删除标记。

## 3. 上下架状态（shangxiaTypes）

名片和科研成果共用 `shangxia_types` 字段，但名片的取值范围更广（含审批流程状态）：

### 3.1 名片的 shangxiaTypes

| 值 | 状态名称 | 含义 |
|:--:|---------|------|
| `1` | **已上架/展示中** | 前台可见的有效名片 |
| `2` | **待审核** | 教师提交新版本后，等待管理员审批 |
| `3` | **已驳回** | 管理员驳回后的状态（同时名片会被软删除） |
| `4` | **已归档** | 被新版本替代后归档（当前版本仍在 mingpian 表，shangxia_types 变为 4） |

### 3.2 科研成果的 shangxiaTypes

| 值 | 状态名称 | 含义 |
|:--:|---------|------|
| `1` | **已上架/展示中** | 前台可见 |

> 科研成果的 `shangxia_types` 在代码中仅用值 `1`，创建时默认设置。
> 代码中没有为科研成果提供独立的审批或上下架切换接口。

### 3.3 前台过滤规则

- 前台公开列表（`/mingpian/list`、`/keyanchengguo/list`）默认仅返回 `shangxia_types=1` 的记录
- 后台列表（`/mingpian/page`）同样默认 `shangxia_types=1`，但支持通过参数覆盖

## 4. 版本控制与审批流程

名片支持完整的版本控制体系，涉及 `mingpian` 主表 + `mingpian_history` 快照表。

### 4.1 教师提交新版本（submitVersion）

**端点**：`POST /mingpian/submitVersion`
**权限**：仅教师角色
**流程**：

```
1. 从 Session 获取当前教师 ID
2. 检查该教师是否已有 shangxia_types=2 的待审记录
   → 如果有，返回 511 "您已有待审版本，请等待审核"
3. 查找当前教师的有效名片（shangxia_types=1）
   → 如果有，新版本号 = 当前版本号 + 1
   → 如果没有，新版本号 = 1
4. 创建新名片记录：
   - shangxia_types = 2（待审核）
   - mingpian_delete = 1（正常）
   - mingpian_clicknum = 1（初始热度）
   - version_number = 计算出的版本号
5. 插入到 mingpian 主表
```

### 4.2 管理员审批通过（approveVersion）

**端点**：`POST /mingpian/approveVersion?id=xxx`
**权限**：仅管理员角色
**流程**：

```
1. 查找 id 对应的名片，验证 shangxia_types = 2（待审核状态）
2. 查找该教师当前生效的名片（shangxia_types=1）
3. 如果存在旧版本：
   a. 将旧版本快照到 mingpian_history 表
      - snapshot_reason = "被新版本V{n}替代"
      - snapshot_time = 当前时间
      - 复制所有字段（排除 id、createTime）
      - mingpian_id 指向旧名片的 ID
   b. 将旧版本 shangxia_types 设为 4（归档）
4. 将新版本 shangxia_types 设为 1（上架）
```

### 4.3 管理员驳回（rejectVersion）

**端点**：`POST /mingpian/rejectVersion?id=xxx&reason=驳回原因`
**权限**：仅管理员角色
**流程**：

```
1. 查找 id 对应的名片，验证 shangxia_types = 2
2. 将被驳回的名片快照到 mingpian_history 表
   - shangxia_types = 3（驳回状态保留到快照中）
   - snapshot_reason = "审核驳回: {reason}"
3. 将主表中该名片 mingpian_delete 设为 2（软删除）
```

### 4.4 版本历史查询（listHistory）

**端点**：`GET /mingpian/listHistory`
- 教师角色自动过滤为自己的历史记录
- 返回按 `version_number DESC` 排序的 `MingpianHistoryView` 列表

## 5. 回退（huitui）约束

**端点**：`POST /mingpian/huitui?historyId=xxx`
**权限**：管理员或教师（教师仅可回退自己的名片）

### 5.1 回退流程

```
1. 根据 historyId 从 mingpian_history 表取出快照
2. 约束检查：
   a. 如果快照不存在 → 返回错误
   b. 如果教师角色但 jiaoshi_id 不匹配 → 返回 "只能回退自己的名片"
   c. 查找该教师当前有效名片（shangxia_types=1）
   d. 如果当前有效版本号 == 快照版本号 → 返回 "该版本已是当前版本"
3. 归档当前版本：
   a. 将当前有效名片快照到 mingpian_history
      - snapshot_reason = "回退到V{n}时被归档"
   b. 将当前有效名片 shangxia_types 设为 4（归档）
4. 恢复历史版本：
   a. 从快照中复制所有字段到 mingpian 主表（新建一条记录）
   b. 设置 shangxia_types = 1（上架）
   c. 设置 mingpian_delete = 1（正常）
```

### 5.2 关键约束总结

| 约束 | 说明 |
|------|------|
| 权限校验 | 教师只能回退自己的名片；管理员可回退任何名片 |
| 重复回退保护 | 当前有效版本号与目标版本号相同时，拒绝回退 |
| 归档保障 | 回退前自动将当前版本存入历史快照 |
| 状态重置 | 恢复的版本自动设为上架（`shangxia_types=1`）且未删除（`mingpian_delete=1`） |

## 6. 软删除 vs 回退 区别说明

教师最常问的问题：**"软删除和回退到底有什么区别？"**

| 对比维度 | 软删除（delete） | 回退（huitui） |
|---------|-----------------|----------------|
| **操作对象** | 当前名片记录 | 历史版本快照 |
| **效果** | 将名片标记为 `mingpian_delete=2`，前后台均不再可见 | 将历史版本恢复为当前有效名片 |
| **原名片** | 保留在主表中，只是被标记 | 当前版本被归档到 history 表 |
| **可恢复性** | 需手动将 `mingpian_delete` 改回 `1`（无专用接口） | 可以再次回退到其他历史版本 |
| **版本记录** | 不产生新的历史快照 | 当前版本被自动快照后归档 |
| **shangxia_types** | 不变（仍为原来的值） | 当前版本变为 4（归档），恢复版本变为 1（上架） |
| **前台影响** | 名片从列表中消失 | 名片内容切换为历史版本的内容 |
| **适用场景** | "不要这张名片了" | "这张名片改坏了，退回到之前的版本" |

### 驳回（reject）与软删除的关系

管理员驳回待审版本时，同时执行两个操作：
1. 将被驳回名片快照到 history 表（`shangxia_types=3`）
2. 将主表中该名片软删除（`mingpian_delete=2`）

因此**驳回 = 快照 + 软删除**，比单纯软删除多了一份历史记录。

## 7. 唯一约束——同一教师能否拥有两张有效名片？

### 结论：不能。系统通过代码逻辑保证每位教师至多拥有一张有效名片。

### 约束实现方式

**创建时**（`/mingpian/save`）：

```java
// 检查同一教师是否已有未删除的名片
Wrapper query = new EntityWrapper()
    .eq("jiaoshi_id", mingpian.getJiaoshiId())
    .eq("mingpian_delete", 1);  // 仅检查未删除的
// 如果存在 → 返回 511 "该老师已有名片"
```

**更新时**（`/mingpian/update`）：

```java
// 排除自身，检查是否有其他未删除的名片
Wrapper query = new EntityWrapper()
    .notIn("id", mingpian.getId())
    .eq("jiaoshi_id", mingpian.getJiaoshiId())
    .eq("mingpian_delete", 1);
// 如果存在 → 返回 511 "该老师已有名片"
```

**提交新版本时**（`/mingpian/submitVersion`）：

```java
// 检查是否已有待审版本
Wrapper query = new EntityWrapper()
    .eq("jiaoshi_id", jiaoshiId)
    .eq("shangxia_types", 2)   // 待审核
    .eq("mingpian_delete", 1);
// 如果存在 → 返回 511 "您已有待审版本"
```

### 边界情况

| 场景 | 主表状态 | 是否允许 |
|------|---------|---------|
| 教师有一张上架名片（`shangxia_types=1`），再创建 | 检查 `mingpian_delete=1` → 有冲突 | 拒绝 |
| 教师有一张待审名片（`shangxia_types=2`），再提交 | 检查 `shangxia_types=2` → 有冲突 | 拒绝 |
| 教师名片被软删除后（`mingpian_delete=2`），创建新名片 | 检查 `mingpian_delete=1` → 无冲突 | 允许 |
| 审批通过后，旧版本变归档（`shangxia_types=4`），新版本上架 | 旧的归档但 `mingpian_delete=1` | 主表中会有两条 `mingpian_delete=1` 的记录，但 `shangxia_types` 不同（4 和 1） |

> **注意**：`/save` 的唯一校验仅检查 `mingpian_delete=1`，不检查 `shangxia_types`。
> 这意味着当教师已有一张归档名片（`shangxia_types=4, mingpian_delete=1`）时，
> 通过 `/save` 创建新名片会被拒绝。归档记录在 `mingpian_delete` 维度仍被视为"存在"。
> 正常流程下应通过 `submitVersion` → `approveVersion` 来更新名片，而非直接 `/save`。

## 8. 点击计数方式（mingpianClicknum）

### 8.1 名片热度计数

**触发端点**：`GET /mingpian/detail/{id}`（前台详情页）

**实现机制**：原子性 SQL 自增

```sql
-- MingpianDao.xml 中的 incrementClickNum
UPDATE mingpian
SET mingpian_clicknum = mingpian_clicknum + 1
WHERE id = #{id}
```

**流程**：
1. 用户访问前台名片详情
2. 先查出名片基本信息
3. 调用 `mingpianService.incrementClickNum(id)` 执行上述 SQL
4. 重新读取名片记录以获取更新后的计数
5. 返回完整的名片详情（含最新热度值）

**特点**：
- 使用数据库原子操作 `clicknum = clicknum + 1`，避免并发丢失更新
- 每次访问详情页都会 +1，无去重（同一用户多次访问会重复计数）
- 初始值在创建时设为 `1`（非 `0`）
- 后台接口 `/mingpian/info/{id}` **不会**触发计数增加

### 8.2 科研成果热度计数

**触发端点**：`GET /keyanchengguo/detail/{id}`（前台详情页）

**实现方式**不同于名片——没有使用原子 SQL，而是应用层读改写：

```
1. 读取当前 keyanchengguoClicknum
2. 设置 keyanchengguoClicknum = 当前值 + 1
3. 调用 updateById() 写回
```

> **注意**：科研成果的计数方式存在并发安全隐患（非原子操作），
> 高并发下可能丢失计数。名片的计数方式更为安全。

### 8.3 创建时的初始值

| 端点 | 初始 clicknum |
|------|:------------:|
| `/mingpian/save`（后台创建） | `1` |
| `/mingpian/submitVersion`（教师提交） | `1` |
| `/mingpian/add`（前台创建） | 不设置（取决于传入值） |
| `/keyanchengguo/save`（后台创建） | `1` |
| `/keyanchengguo/add`（前台创建） | 不设置 |

## 9. 科研成果与名片的联合展示

### 聚合逻辑

当用户访问前台名片详情（`GET /mingpian/detail/{id}`）时，系统会自动聚合该教师的全部有效科研成果：

```
1. 获取名片对应的 jiaoshi_id
2. 查询 keyanchengguo 表，条件：
   - jiaoshi_id = 名片所属教师
   - keyanchengguo_delete = 1（未删除）
   - shangxia_types = 1（已上架）
3. 将符合条件的科研成果列表附加到名片视图的 keyanchengguoList 字段
4. 返回包含科研成果的完整名片详情
```

### 数据结构

```json
{
  "code": 0,
  "data": {
    "id": 1,
    "mingpianName": "张三教授名片",
    "mingpianXingming": "张三",
    "jiaoshiName": "张三",
    "mingpianClicknum": 42,
    "keyanchengguoList": [
      {
        "id": 10,
        "keyanchengguoName": "基于深度学习的图像识别研究",
        "keyanchengguoTypes": 1,
        "keyanchengguoClicknum": 15,
        "shangxiaTypes": 1
      },
      {
        "id": 11,
        "keyanchengguoName": "分布式系统容错机制",
        "keyanchengguoTypes": 2,
        "keyanchengguoClicknum": 8,
        "shangxiaTypes": 1
      }
    ]
  }
}
```

> **注意**：科研成果的独立详情页（`/keyanchengguo/detail/{id}`）不会反向聚合名片信息。
> 联合展示仅在名片详情页中单向发生。

```
               └──────────────┘                  │
                      │                          │
                      │  从 history 恢复          │
                      │  huitui                  │
                      ▼                          │
               ┌──────────────┐                  │
               │ 恢复为上架    │──────────────────┘
               │ shangxia=1   │  如果再次回退
               │ delete=1     │  当前版本再次归档
               └──────────────┘
```

### 10.2 版本流转时序图

```
时间线 ────────────────────────────────────────────────────────►

教师A创建名片V1
  │  mingpian表: {id:1, version=1, shangxia=1, delete=1}
  │
  ├── 教师A提交新版V2（submitVersion）
  │   mingpian表: {id:1, version=1, shangxia=1, delete=1}  ← 旧版不动
  │               {id:2, version=2, shangxia=2, delete=1}  ← 新增待审
  │
  ├── 管理员审批通过（approveVersion id=2）
  │   mingpian_history: {mingpianId:1, version=1, reason="被新版本V2替代"}
  │   mingpian表: {id:1, version=1, shangxia=4, delete=1}  ← 旧版归档
  │               {id:2, version=2, shangxia=1, delete=1}  ← 新版上架
  │
  ├── 管理员回退到V1（huitui historyId=xxx）
  │   mingpian_history: +{mingpianId:2, version=2, reason="回退到V1时被归档"}
  │   mingpian表: {id:1, version=1, shangxia=4, delete=1}  ← 不变
  │               {id:2, version=2, shangxia=4, delete=1}  ← V2被归档
  │               {id:3, version=1, shangxia=1, delete=1}  ← V1恢复为新记录
  │
  └── ... 可继续回退或提交新版本
```

### 10.3 名片 vs 科研成果的删除对比

## 11. 收藏表（Collection）说明

### 11.1 名片收藏（mingpian_collection）

- 学生可通过 `/mingpianCollection/add` 收藏名片
- 唯一约束：同一学生 + 同一名片 + 同一收藏类型，不可重复收藏
- 重复收藏返回 `511 "您已经收藏过了"`
- 删除为硬删除（物理删除行）

### 11.2 科研成果收藏（keyanchengguo_collection）

- 逻辑与名片收藏完全对称
- 唯一约束：同一学生 + 同一科研成果 + 同一收藏类型
- 重复收藏返回 `511 "您已经收藏过了"`
- 删除为硬删除
